## Purpose

Submit a Pull Request to Azure DevOps (ADO REST API) or GitHub (GitHub REST API /
`gh`), or produce a complete PR draft artifact for manual submission. The git remote
provider is auto-detected (Step 0.5) and only the *transport* (endpoint, auth, base
branch, URLs) differs — the work-item ID, ICEA gate, secrets gate, and findings gate are identical
on both. This skill completes the end-to-end PR workflow:
`pr-describe` → `pr-create` → `pr-spec-review`.

Compliance checks and the findings gate **always run on both paths** — no PR
artifact is produced without passing (or explicitly acknowledging) these gates.

**Requires:** An ICEA-validated PR description already generated by the `pr-describe`
skill in this conversation. Do not create PRs without a validated description.

## Flag handling — check before Step 1

```bash
# Parse flags from the invocation arguments
OFFLINE=false
RELEASE_ID=""
SPRINT_ID=""
SKIP_ICEA=false
SKIP_SECURITY=false

for arg in "$@"; do
  case "$arg" in
    --offline)          OFFLINE=true ;;
    --release)          RELEASE_ID="$2"; shift ;;
    --sprint)           SPRINT_ID="$2"; shift ;;
    --skip-icea-check)  SKIP_ICEA=true ;;
    --skip-security-gate) SKIP_SECURITY=true ;;
  esac
  shift
done
```

**If `--offline` is present but `--release` or `--sprint` is missing — hard stop:**

```
❌ --offline requires --release <ID> and --sprint <ID>
   Example: /pr-create --offline --release 3 --sprint 42
```

Do not continue. Exit immediately.

## Step 0.5 — Detect the git remote provider

Runs on both paths. No connection required — reads local git config only.

Read `.claude/plugin-path.txt` to get `PLUGIN_DIR` (if absent, use the §1a resolver), then
read `$PLUGIN_DIR/skills/shared/git-remote-provider-spec.md` and run its helpers. Capture
each printed value and substitute it as a literal placeholder in later steps (do **not**
rely on shell variables persisting across command lines):

- `detect_git_provider` → `{provider}` ∈ `ado | github | other`.
- Parse identifiers from `git remote get-url origin`:
  - `github` → `{owner}` / `{repo}`
  - `ado` → `{org}` / `{project}` / `{repo}` (Step 6 table)
- `{provider} = other` → API submit is not supported; force the **draft path** (Step 8)
  and tell the developer their remote host isn't supported for direct submission.

## Step 1 — Resolve PR content from local sources

This step runs on both paths. No connection required.

**Branch and target:**
```bash
git symbolic-ref --short HEAD                    # source branch
```

Resolve `{base-branch}` via the provider spec's base-branch policy:
- `ado` → `dev` if `git ls-remote --heads origin dev` is non-empty, else **ask**
  "What is the target branch for this PR?"
- `github` / `other` → the remote default branch (`resolve_remote_default_branch`) if it
  exists, else **ask**.

**Source-branch-pushed guard** (prevents GitHub 422 / ADO 400 at submit):
```bash
git ls-remote --heads origin "<source-branch>"   # must be non-empty
```
If empty, stop:
> "Your branch isn't on the remote yet. Push it first:
> `git push -u origin <source-branch>`, then re-run `/pr-create`."

Extract the ADO work item ID from the branch name (pattern: `ADO-[0-9]+`).
If no ID found in the branch name, ask: "What is the ADO work item ID for this PR?"
(The ADO-{ID} identifies the work regardless of provider — it is required on GitHub too.)

**PR description:**
Check the current conversation for a PR description generated by `pr-describe`.
It will begin with a heading matching `## [ADO-ID] ...`.

- If found: extract the first heading line as the PR title, full markdown body as description.
- If not found: stop and output:
  > "No `pr-describe` output found in this conversation. Run `/pr-describe` first to
  > generate an ICEA-validated PR description, then run `/pr-create`."

**ICEA file:**
```bash
find docs -name "ADO-<ID>-*.icea.md" 2>/dev/null | head -1
```

Read it if found. Note "No ICEA found" if absent — the compliance check will handle this.

**Report scope:**
```
📋 PR scope
  Provider: <ado | github | other>
  Source  : <source-branch>
  Target  : <base-branch>
  ADO     : #<ID>
  ICEA    : docs/Release{R}/Sprint{S}/UserStory{ID}/ADO-<ID>-<name>.icea.md  (or: not found)
  Title   : <derived from pr-describe output>
```

## Step 2 — ICEA compliance check

Always runs. No connection required.

```bash
git diff <base-branch>..HEAD --stat
```

Invoke the single compliance engine `pr-spec-review` in compact mode:

```
Read .claude/plugin-path.txt to get PLUGIN_DIR (if absent, use §1a resolver), then
Read $PLUGIN_DIR/skills/pr-spec-review/SKILL.md and run it against the current branch
diff. Scope: ICEA + Tech Spec when an approved `ADO-{ID}-*.techspec.md` exists for this
ADO ID, else `--icea-only`. Output: `--compact` (verdict block only — omit the four-part
report at this stage).
```

**Based on the verdict:**

| Verdict | Action |
|---|---|
| ✅ PASS | Proceed to Step 2b |
| ⚠️ WARN | Carry warnings forward to Step 6 prompt — non-blocking |
| ❌ FAIL | Stop entirely. Do not proceed to secrets/findings gate or ADO prompt. |

**On FAIL:**

```
❌ PR CREATION BLOCKED — ICEA compliance check failed

  {list of Critical findings from pr-spec-review}

Required action:
  Fix the above issues OR update the ICEA to cover them before creating the PR.

  To override (not recommended):
  Re-run with --skip-icea-check to bypass this gate.
  This will be noted in the PR description and the draft artifact.
```

**On `--skip-icea-check`:** proceed, carry a bypass note forward into both the
PR description and the draft artifact:
```
⚠️ ICEA compliance check bypassed by developer.
```

## Step 2b — Secrets gate (hard, non-skippable)

Always runs. No connection required. There is **no** override flag — a pushed credential is
irreversible; `--skip-icea-check` / `--skip-security-gate` do NOT bypass this gate.

Load `$PLUGIN_DIR/skills/shared/secrets-scan-spec.md` and run its canonical functions verbatim
against the branch diff (the spec's `pr-create` invocation):

```bash
changed=$(git diff --name-only <base-branch>..HEAD)
sens=$(printf '%s\n' "$changed" | scan_sensitive_paths)
data=$(printf '%s\n' "$changed" | scan_static_dir_paths)
hits=$(git diff <base-branch>..HEAD | scan_secret_content)
```

If any of `$sens` / `$hits` / `$data` is non-empty → STOP. Emit the spec's **pr-create** output
block and do not proceed to the findings gate or ADO prompt. Otherwise carry `Secrets: ✅ clean`
forward to Step 5.

## Step 3 — Findings gate

Always runs. No ADO connection required.

Load `$PLUGIN_DIR/skills/shared/findings-gate.md` and execute the canonical bash functions
defined there verbatim. Do not re-implement the ledger-walking logic inline.

Collect:
- `cr_open`, `sec_open`, `ds_open` — open Critical/High FP IDs per ledger
- `total_open` — sum across all three ledgers
- `cr_dismissed`, `sec_dismissed`, `ds_dismissed` — accepted-risk dismissals

Carry all results forward to Step 6. Do not output anything here — the findings
summary is shown as part of the Step 6 ADO connection prompt.

**If `--skip-security-gate` is present:** mark the gate as bypassed, record the
developer's justification, carry forward to Step 6 and the draft artifact.

## Step 5 — Ask developer: connect and submit, or save draft?

Only reached if `--offline` is NOT set.

**If `{provider} = other`:** skip this prompt — API submit is unsupported for the detected
host. Go straight to the draft path (Step 8) and say so.

Display the compliance and findings summary first, then ask (use the provider name from
Step 0.5 — "Azure DevOps" or "GitHub"):

```
📋 Pre-submission summary
  Provider        : <Azure DevOps | GitHub>
  Spec compliance : ✅ PASS  (or ⚠️ N warnings)   ← pr-spec-review --compact
  Secrets         : ✅ clean
  Open findings   : N Critical/High across all ledgers  (or: ✅ None)

Connect to <provider> and submit the PR, or save a PR draft for manual submission?

  1) Connect and submit
  2) Save PR draft only

Enter 1 or 2:
```

Wait for explicit input. Do not default to either option.

**If findings gate has `total_open > 0` and `--skip-security-gate` is NOT set:**
Display the findings gate warning block from `findings-gate.md` (`pr-create` variant)
above the prompt and require the developer to respond `yes / fix-first / no` before
the connect/draft question is shown.

- `fix-first` → stop, list FP IDs
- `no` → cancel entirely
- `yes` → carry acknowledgement forward, show connect/draft prompt

## Step 6 — Connect path: resolve credential and remote details

Only reached if developer chose option 1 in Step 5. **Branch on `{provider}` from Step 0.5.**
Never echo, store, or log any credential value on either path.

---

### 6·ADO — `{provider} = ado`

#### PAT resolution

| Option | How | When to use |
|---|---|---|
| **A — Windows User Environment Variable** | `AZURE_DEVOPS_PAT` user env var | Default for all developers |
| **B — `.claude/settings.json`** | `{ "env": { "AZURE_DEVOPS_PAT": "..." } }` — must be gitignored | Acceptable for local dev only |
| **C — Paste at prompt** | Entered interactively | Emergency only |

```bash
echo $AZURE_DEVOPS_PAT
```

- If set and non-empty: use silently.
- If not set: prompt the developer to paste it for this request only.

See `$PLUGIN_DIR/skills/pr-create/references/ado-api-guide.md` for PAT scope requirements.

#### ADO connection details

```bash
git remote get-url origin
```

Parse `org`, `project`, `repo` from the remote URL:

| URL format | Example |
|---|---|
| `https://dev.azure.com/{org}/{project}/_git/{repo}` | Modern |
| `https://{org}.visualstudio.com/{project}/_git/{repo}` | Legacy |
| `https://{org}@dev.azure.com/{org}/{project}/_git/{repo}` | With username prefix |

If parsing fails: ask for org, project, and repo individually.

#### Enrich PR title from ADO work item

```bash
curl -s --ssl-no-revoke \
  "https://dev.azure.com/{org}/{project}/_apis/wit/workitems/{ID}?api-version=7.1&\$select=System.Title" \
  -H "Authorization: Basic $(printf ':%s' "$AZURE_DEVOPS_PAT" | base64 -w 0)"
```

If the ADO title differs from the branch-derived title, use the ADO title.
If the call fails, keep the branch-derived title and note it in the output.

---

### 6·GitHub — `{provider} = github`

#### Token resolution

| Option | How | When to use |
|---|---|---|
| **A — Windows User Environment Variable** | `GITHUB_TOKEN` user env var | Default for all developers |
| **B — `.claude/settings.local.json`** | `{ "env": { "GITHUB_TOKEN": "..." } }` — gitignored (never `settings.json`) | Local dev only |
| **C — Paste at prompt** | Entered interactively | Emergency only |
| **D — `gh` CLI** | If `command -v gh` and `gh auth status` succeed | Fast-path; `gh` handles auth |

```bash
echo $GITHUB_TOKEN
command -v gh >/dev/null 2>&1 && gh auth status >/dev/null 2>&1 && echo "gh available"
```

- Prefer `gh` if available and authenticated (no token handling needed).
- Otherwise use `GITHUB_TOKEN`; if unset and `gh` unavailable, prompt for the token for
  this request only.

`{owner}` / `{repo}` were parsed in Step 0.5. See
`$PLUGIN_DIR/skills/pr-create/references/github-api-guide.md` for token scopes.

#### Title
GitHub has no ADO work-item title API. Keep the `pr-describe`/branch-derived title as-is;
the `ADO-{ID}` stays a textual reference in the title/body (no native work-item link).

## Step 7 — Connect path: confirm and submit

Display confirmation and wait for explicit "yes":

```
About to create PR:

  Provider: <Azure DevOps | GitHub>
  From    : <source-branch>
  Into    : <base-branch>
  Repo    : <org>/<project>/<repo>  (ADO)  |  <owner>/<repo>  (GitHub)
  Title   : <title>
  WI      : ADO #<id>   (GitHub: textual reference only — no native link)
  ICEA    : <verdict>
  Findings: <N open Critical/High — acknowledged>  (or: ✅ None)

Proceed? (yes / no)
```

If anything other than "yes": cancel.
> "PR creation cancelled. Your description is saved in this conversation — run
> `/pr-create` again when ready."

**Submit — `{provider} = ado`:**

```bash
curl -s --ssl-no-revoke -4 -w "\n%{http_code}" -X POST \
  "https://dev.azure.com/{org}/{project}/_apis/git/repositories/{repo}/pullrequests?api-version=7.1" \
  -H "Content-Type: application/json" \
  -H "Authorization: Basic $(printf ':%s' "$AZURE_DEVOPS_PAT" | base64 -w 0)" \
  -d '{
    "title": "{title}",
    "description": "{description}",
    "sourceRefName": "refs/heads/{source-branch}",
    "targetRefName": "refs/heads/{base-branch}",
    "workItemRefs": [{"id": "{work-item-id}"}]
  }'
```
- HTTP 201 → extract `.pullRequestId` — record the ADO↔PR link in the governance audit trail
  (best-effort, never blocks), then proceed to Step 9:
  ```bash
  node .claude/hooks/audit-append.cjs "{\"event\":\"pr.linked\",\"ado\":\"${ADO_ID}\",\"pr_id\":${PR_ID},\"repo\":\"{repo}\",\"result\":\"created\",\"source\":\"pr-create\"}" 2>/dev/null || true
  ```
  This link lets the reconcile step (in /sprint-metrics) later attach the ADO-verified
  lead/product approver votes to this ADO id.
- HTTP 409 (PR already exists) → print the conflict message and stop.
- Any other status → extract `.message`, show error, suggest `$PLUGIN_DIR/skills/pr-create/references/ado-api-guide.md`.

**Submit — `{provider} = github`:** if `gh` was selected in Step 6, use
`gh pr create --base {base-branch} --head {source-branch} --title "{title}" --body-file -`
(description on stdin). Otherwise curl:

```bash
curl -s --ssl-no-revoke -4 -w "\n%{http_code}" -X POST \
  "https://api.github.com/repos/{owner}/{repo}/pulls" \
  -H "Accept: application/vnd.github+json" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -d '{
    "title": "{title}",
    "body": "{description}",
    "head": "{source-branch}",
    "base": "{base-branch}"
  }'
```
- HTTP 201 → extract `.html_url` and `.number` — proceed to Step 9.
- HTTP 422 "already exists" → print the existing PR and stop (same handling as ADO 409).
- Any other status → extract `.message`, show error, suggest `$PLUGIN_DIR/skills/pr-create/references/github-api-guide.md`.

**On the remote unreachable (network error, non-HTTP failure):** do not hard fail.
Inform the developer and fall through to Step 8 (draft output) automatically:

```
⚠️ Submission failed — could not reach <provider>.
   Saving PR draft artifact instead.
```

**If `--offline`:** use `RELEASE_ID` and `SPRINT_ID` from arguments. Already validated.


## Hard rules

- NEVER store, echo, or log the credential value (PAT / token) at any point
- ALWAYS detect the git remote provider (Step 0.5) before any submit; `{provider} = other` is draft-only
- NEVER produce a PR artifact (submitted or draft) without running Steps 2, 2b, and 3 first
- NEVER skip the compliance check, secrets gate, or findings gate — all run on both paths
- NEVER proceed past a FAIL pr-spec-review verdict unless `--skip-icea-check` is present
- NEVER bypass the secrets gate (Step 2b) — it has no override flag
- NEVER default the connect/draft question — wait for explicit developer input
- NEVER write the draft artifact with a partial path — both Release ID and Sprint ID required
- NEVER create the PR without explicit "yes" at Step 7 confirmation
- NEVER proceed if `pr-describe` has not been run — unvalidated descriptions must not be submitted
- If the source branch is not pushed to the remote: stop and tell the developer to `git push -u origin <branch>` first
- If source branch equals target branch: abort — "Source and target branches are the same. Switch to your feature branch before creating a PR."
- If a PR already exists for this branch (ADO HTTP 409 / GitHub HTTP 422): output the conflict message and stop — do not attempt to update the existing PR
- On the remote unreachable during submit: fall through to draft path automatically — do not hard fail
- ALWAYS note gate overrides (`--skip-icea-check`, `--skip-security-gate`) in both the PR description and the draft artifact

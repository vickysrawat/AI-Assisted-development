For developers using the plugin

What this plugin is

A spec-first development workflow for teams on Azure DevOps. Every feature starts from an approved ICEA (Intent · Context · Examples · Acceptance); code generation is gated on it, every PR is compliance-checked before it opens, and the plugin keeps a memory of your project's decisions between sessions — all inside Claude Code.

◻
Spec-first
No feature code is written until an ICEA is approved on disk. The gate is enforced mechanically, not by convention.
⚖
Quality-gated
A critic reviews each artefact as it is produced; code-review, security, and a pre-commit check guard what lands.
◌
Remembers
The Dream memory system consolidates decisions and gotchas so the next session starts with context, not a blank slate.
◈
Stack-aware
Detects your stack per repo — .NET (Framework 4.x → .NET 10), Java/Spring, Python, Node.js, Angular, React — and loads matching rules.
ℹCore principle: do not over-complicate. The plugin stops and asks when something is ambiguous rather than guessing, and it documents non-trivial choices as it goes.
⚠Maintaining or extending the plugin itself (adding skills/commands, releasing a version)? That lives in the Plugin Developer Guide, not here.
Getting started · step 1

Azure DevOps PAT

Skills that read or write work items, PRs, and metrics authenticate with a Personal Access Token. Create one before first use.

ScopeWhy
Work Items (Read & Write)Read ICEA work items, create task breakdowns, log bugs.
Code (Read & Write)Read the diff and open pull requests.
Pull Request Threads (Read & Write)Post PR descriptions and review threads.

Create it at Azure DevOps → User settings → Personal access tokens → New Token, then store it — best option first:

A
Windows environment variable (recommended)
Best

Set AZURE_DEVOPS_PAT as a user environment variable. It never touches the repo and is shared across projects.

B
.claude/settings.local.json (gitignored)
Alternative

Add it under env in .claude/settings.local.json, which is gitignored. Never put it in the committed settings.json — a write-time and pre-commit guard block secrets there.

⚠Never commit a PAT. If one is ever staged into .claude/settings.json, the secrets guard blocks the commit.

Getting started · step 4

Health check

Run setup-status any time to confirm the plugin is wired up. It reports 🟢/🟡/🔴 across 23 infrastructure checks — CLAUDE.md, memory, rules, stubs, architecture docs, the knowledge graph (index + freshness + stale flag), the deployment doc, caches, ignore-file coverage, open findings across all ledgers, model-version hygiene, and plugin-version drift — and prints a prioritised action list. After a plugin upgrade it flags UPGRADE PENDING; run setup-sync to re-provision.

Build features

The ICEA workflow

This is the day-to-day loop. You never write feature code first — you agree the spec, then Claude implements exactly that. The gate is enforced by a rule pre-loaded each session and a server-side PR check, so it cannot be quietly skipped.

1 · planDescribe the feature
→
2 · ICEADraft + SAVE PLAN
→
3 · Tech SpecSAVE ICEA → SAVE TECH
→
4 · approveAPPROVE ADO-{ID}
→
5 · buildIMPLEMENT ADO-{ID}
1 · Start
Run icea-feature (or describe a feature / paste an ADO #). Claude asks clarifying questions and drafts the plan. It will not generate code yet.
2 · ICEA
Reply SAVE PLAN ADO-{ID} to persist the plan and draft the ICEA (Intent · Context · Examples · Acceptance). The critic checks it before it is written for your review.
3 · Tech Spec
SAVE ICEA ADO-{ID} runs the critic gate and drafts the Tech Spec; SAVE TECH ADO-{ID} writes it (blocks on unresolved open questions).
4 · Approve
Your tech lead reviews the docs on disk and you reply APPROVE ADO-{ID}. Only this exact word unblocks code generation.
5 · Implement
IMPLEMENT ADO-{ID} generates code for the approved ICEA (Epics go story by story). Every write still passes the Write Gate.
Any time · Status
STATUS ADO-{ID} shows exactly where a work item is and the next action — the perfect re-entry point after a break.

Change tiers — you never pick one

The plugin classifies each change mechanically so small work isn't buried in ceremony:

  • T1 micro (≤1 file, ≤20 lines, no signature/dependency/sensitive-path changes): a one-line auto-ICEA is written and work proceeds immediately. The critic still reviews the result. Say STOP to force a full ICEA.
  • T2 standard: the full ICEA draft → APPROVE cycle.
  • T3 elevated (auth paths, public endpoints, new dependencies, sensitive data, schema changes): full ICEA plus mandatory permission-boundary examples.

Tiers only move up: if a T1 change grows past its bounds, checkin blocks the commit and routes you to a full ICEA. A change manifest lists every file the model expects to touch before any code exists; at check-in the prediction is scored against the real diff to improve future predictions (it never blocks).

Emergency bypass

⚠Prefix your message with /skip-icea to bypass the Feature Gate. Claude warns once and proceeds; the bypass is logged and audited. Not recommended for regular use — it lifts only the Feature Gate, never the Write Gate, secrets scan, or findings gate.
Build features

The critic layer

The critic is a second-pass reviewer that checks an artefact at the moment it is produced, before it is saved. It runs automatically at three points and can also be run on demand with critic.

GateWhenWhat it checks
ICEA draftBefore the ICEA is written for reviewCompleteness, testability, B1–B7 coverage, scope vs Intent. Auto-revises up to 2×.
Tech Spec draftBefore the Tech Spec is writtenICEA↔design traceability, coverage-matrix completeness, decision-option fidelity.
Generated codeAfter code is generated, before any file is writtenICEA + Tech Spec traceability (three-way: intent → plan → code; ICEA wins on conflict), simplicity, rules compliance, decision transparency, hidden assumptions.
ℹWhy a critic when there's already code review? Code review runs on files that already exist — the spec is out of context by then. The critic runs while the ICEA, the Tech Spec, and the fresh code are all in front of Claude, so it can ask the one thing a later scan can't: does this do exactly what the approved AC asked and what the Tech Spec planned — no more, no less?
Quality & delivery

Quality & security

Findings from every scanner are fingerprinted (FP-xxxxxxxx) into per-tool ledgers, so a finding is tracked across runs — fix it with fix or suppress it with dismiss (with a required justification).

code-review
Static-analysis-style review with cross-run tracking — new defects flagged, fixed ones marked with git attribution. Scope flags: --changed --pr --full --ci --area.
security-review
OWASP/CVSS/CWE review; a static asset audit runs first (flags real data in public/). Business-context severity can escalate findings. Same scope flags.
dynamic-scan
Runtime DAST via OWASP ZAP in Docker against a running app/API. Safe passive by default; --full/--scope for gated active scans.
checkin
Pre-commit gate: code-review + ICEA compliance + secrets scan + open Critical/High findings, in one pass. Emits a pre-filled commit command when green.
ℹRun a flag-taking scanner with no flag and it shows a short menu with the sensible default pre-selected. In CI / non-interactive runs there is no prompt — the documented default is used.

Bigger moves

Migrate an application

There is no single "migrate" command — pick by what is actually changing. Each is ledger-backed with its own RESUME and STATUS.

⬆️
upgrade
same stack, higher version
In-place bump (e.g. .NET 6 → 8, Angular 15 → 17). Orchestrates the stack-native tool and delivers a decision-grade Gap + Risk report; a false-upgrade (cross-runtime) is routed to /rewrite.
🔀
rewrite
different stack
Generative translation into a NEW target-folder app (e.g. Java → .NET, Express → Angular). Posture → options → per-cluster Behavioral Assurance Level (BAL) → two-gate merge/completion. Source stays read-only.
☁️
replatform
new host (on-prem → cloud)
Moves where the app runs. The LLM authors IaC + runbooks; a human executes anything touching real infra/data. Graded against an NFR + Well-Architected oracle.
🧭
knowledge-freshness
keep advice current
Validates and (with approval) refreshes the migration family's offline reference knowledge. Modes: check | refresh.

Bigger moves

Understand the codebase

The plugin keeps a lightweight map of your codebase under .claude/graph/ — an index plus one small detail file per module. Skills read this map for fast orientation instead of scanning source, which keeps token cost down on large repositories.

explain
Answers "where does X live / what depends on Y" from the architecture docs and knowledge graph — no source scanning by default. Tells you exactly which file to open for detail.
graph-sync
Refreshes the graph incrementally — only stale modules regenerate. A git hook flags staleness after a pull; setup-status surfaces it.
graph-viz
Renders an offline HTML map of modules, dependencies, and hot-spots. --3d for a WebGL view.
update-arch
Refreshes the prose architecture docs for changed areas; --deployment re-runs the questionnaire.
Memory

Memory — the Dream system

Dream consolidates what happened in your sessions into durable project memory, so the next session starts with the decisions, conventions, and gotchas already loaded — not a blank slate. It proposes changes and waits for tiered approval before writing.

Phase 1Read sessions
→
Phase 2Score entries
→
Phase 3Propose ADD/UPDATE/DELETE
→
Phase 4Tiered approval
→
Phase 5Write memory
dream
Run a consolidation pass every 5–8 sessions. Proposes operations with justification; you approve by tier.
dream-health
A browser dashboard (memory/health.html) of confidence scores, the decay curve, and promote candidates.
dream-audit
Quarterly quality audit — flags uncited facts and contradicted promotions, feeding rollback history into scoring.
dream-rollback
Reverts a specific /dream run from the audit trail. Auditable and itself reversible.

Keyword reference

These keywords work in any message — no slash command needed. The ADO ID is case-insensitive.

KeywordWhat it does
SAVE PLAN ADO-{ID}Persist the plan and draft the ICEA.
SAVE ICEA ADO-{ID}Run the critic gate, save the ICEA, and draft the Tech Spec.
SAVE TECH ADO-{ID}Write the Tech Spec (blocks on open questions).
APPROVE ADO-{ID}Approve the ICEA + Tech Spec and unblock code generation. APPROVE ADO-{ID} Story-{N} for one story.
APPROVE ALL ADO-{ID}Standing Write-Gate approval for the current plan — still shows each diff, just no per-file pause. REVOKE ALL ADO-{ID} cancels it.
IMPLEMENT ADO-{ID}Generate code for the approved ICEA (optionally Story-{N}).
REVISE ADO-{ID}Revise the ICEA/Tech Spec and re-gate code generation.
STATUS ADO-{ID}Show current state and the exact next action.
BUG ADO-{ID} — {description}Log a bug entry for that work item.
UPGRADE / REWRITE / REPLATFORM ADO-{ID}Start a migration; each also has … RESUME and … STATUS.
SET DOMAINInfer/confirm the business domain so business-context severity is tuned to your domain.

For plugin maintainers

Why this exists

This guide is for people who maintain or extend the plugin itself — adding commands and skills, authoring rules, changing governance, and cutting releases. If you are looking for how to use the plugin in a project, see the User Guide.

The plugin accreted from a real problem: LLM coding assistants are fast but unaccountable. Each layer here solves a failure the last one exposed — the ICEA gate stops unspecced code; the critic catches spec/scope drift before it reaches disk; the Write Gate keeps a human in the loop on every file; scoped rules keep generated code idiomatic per stack; and the Dream memory keeps decisions from evaporating between sessions. The guiding constraint is simplicity: prefer a deterministic script over a prompt, a single source of truth over duplicated copies, and an explicit gate over a hopeful convention.

ℹDesign decisions live as append-only ADRs under docs/adr/. When you make a non-trivial architectural call, add one.

How it all fits

Everything is declared in .claude-plugin/plugin.json — the single source of truth for the version and the component manifest. At a glance the plugin ships:

46 commands
Slash commands — thin entry points that invoke a skill or a command-delegation flow.
48 skills
The behaviour. Each is a skills/<name>/SKILL.md (+ optional references/).
43 rules
Frontmatter-scoped coding rules that auto-load per file type from a layered set.
47 shared specs
Cross-skill primitives under skills/shared/ — the contracts skills reuse.
2 subagents
bc-searcher · bc-synthesizer (business-context grounding).
Runtime hooks + CI
Deterministic gates that enforce the floor even when a client bypasses a prompt.
⚠Counts are authoritative from plugin.json — never hand-type them into docs. tests/validate.js checks that on-disk components match the manifest.

Component model

Commands

A command is a thin stub registered in plugin.json → components.commands. The deployable stub lives in _project-deploy/commands/<name>.md with quoted description, an argument-hint, a --help block, and a fully-qualified <skill>ai-assisted-development:<name></skill> delegation. setup-init deploys all 46 stubs into a project's .claude/commands/ so they appear in the VS Code picker. For what each command does, see the User Guide's command reference — this guide does not duplicate it.

Component model

Skills

Skills carry the behaviour. Each is skills/<name>/SKILL.md with a metadata line that declares its version, last-changed date, plugin compatibility, and a consent category.

ConsentMeaning
AMay read source freely (e.g. code generation, migration authoring).
BReads source only after announcing intent (evidence-derived doc generators).
CNever reads application source — only reports, ledgers, architecture, and state.

The authoritative table is skills/shared/source-file-consent.md; validate.py errors if a SKILL.md's token disagrees with it. Skills route to models by task type (see Model routing) and reason through named expert personas kept consistent across the suite.

Component model

Rules

Rules are stack-scoped coding standards in _project-deploy/rules/ (43 files), organised as a layered set — base backend/frontend layers plus per-stack and per-ecosystem overrides. Each carries frontmatter that scopes it to file globs so Claude Code auto-loads only the relevant ones when editing a matching file.

Deployment is driven by scored stack-key detection (ADR 0059) so a .NET 10 API never draws legacy framework rules; the frontmatter/layering model is ADR 0042 / ADR 0043. The data-access rule is a hard one: parameterised queries only, never string-built SQL.

Component model

Shared specs

47 cross-skill primitives live under skills/shared/ and are registered in plugin.json → components.shared. They are the contracts multiple skills reuse — e.g. write-gate-spec.md, model-routing-spec.md, source-file-consent.md, multi-root-scan.md, scope-flags-spec.md, flag-prompt-spec.md, the migration ledger schema, and the offline migration-knowledge/refs/ tier.

⚠A shared spec is a single source of truth. When you add one, register it in components.shared — validate.js fails on a spec that is on disk but unregistered, and the README's shared-specs table is generated from the manifest (ADR 0063).
Component model

Hooks & subagents

Prompt-level gates are backed by deterministic hooks so the floor holds even if a client ignores an instruction: a write-blocker (icea-floor) when no approved ICEA exists, a git pre-commit hook that blocks commits with open Critical/High findings, and a CI script that fails the pipeline on ledger-integrity violations. validate-pr-compliance.py runs as a required branch-policy check server-side — unbypassable from any client. Hooks install by default during setup-init, their integrity is monitored by setup-status, and they re-sync on every version bump.

Two subagents ship under agents/: bc-searcher (regulatory-grounding web search, no project-file access) and bc-synthesizer (combines cited categories with local architecture, no network) — the split keeps project data off the network during business-context generation.

Governance & graph

Gates & governance

The governance rails are defined in CLAUDE.md and enforced by hooks + CI. As a maintainer, know the three orthogonal gates:

Feature Gate (ICEA)
No implementation code for a new capability without an approved ICEA on disk. Output-gated; overridable only via the loud, audited /skip-icea / SKIP_ICEA_FLOOR.
Write Gate
Source/config is never written until APPROVE ADO-{ID}. Boundary-crossing writes (outside the repo root) always confirm and are not blanketed by APPROVE ALL.
Findings gate
Open Critical/High findings block checkin and PR creation; never blanket-skippable.
Critic planning gates
The critic fires at the ICEA draft, the Tech Spec draft, and generated code — before each is written (ADR 0052).

Every gate block, bypass, approval, and dismissal is recorded in a tamper-evident audit trail under .claude/audit/.

Governance & graph

Knowledge graph internals

The codebase knowledge graph in .claude/graph/ is the single orientation layer. graph.json is the authoritative structure — typed nodes/edges with confidence, module-wide staleness fingerprints, and an absent-tolerant sourceRoot for multi-root repos — and the markdown index + per-module detail files are its projection (ADR 0039).

EXTRACTED dependency edges are derived deterministically from source imports by scripts/graph-extract-edges.js (not by the model), so they are parser-true and byte-stable and source never enters context (ADR 0041); the model authors only INFERRED/AMBIGUOUS edges. module-derive.cjs derives the module skeleton (multi-root aware via multi-root-scan.md); graph-create builds the initial graph at setup and graph-sync refreshes it incrementally.

Release & version

.claude-plugin/plugin.json → version is the single source of truth. Never edit derived copies by hand.

Bump
node scripts/bump-version.js X.Y.Z
Writes plugin.json, propagates the CLAUDE.md label, prepends a CHANGELOG stub, and warns about stale guide/README stamps.
Fill the CHANGELOG
CHANGELOG.md
Describe what changed, which files, and why. validate.py requires an entry for the current version.
Write a migration note
docs/migrations/NNN-X.Y.Z.md
For version-sensitive changes, so setup-sync can apply exactly the deltas in range for existing projects.
Guard
node scripts/check-version-consistency.js
Must be green — re-stamp the guides' documents-plugin-version and the README header when you touch their content.

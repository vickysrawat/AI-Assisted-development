For plugin maintainers

Why this exists

This guide is for people who maintain or extend the plugin itself — adding commands and skills, authoring rules, changing governance, and cutting releases. If you are looking for how to use the plugin in a project, see the User Guide.

The plugin accreted from a real problem: LLM coding assistants are fast but unaccountable. Each layer here solves a failure the last one exposed — the ICEA gate stops unspecced code; the critic catches spec/scope drift before it reaches disk; the Write Gate keeps a human in the loop on every file; scoped rules keep generated code idiomatic per stack; the RBAC layer ensures only authorised roles can approve elevated actions; the governance audit trail makes every approval tamper-evident; and the Dream memory keeps decisions from evaporating between sessions. The guiding constraint is simplicity: prefer a deterministic script over a prompt, a single source of truth over duplicated copies, and an explicit gate over a hopeful convention.

ℹDesign decisions live as append-only ADRs under docs/adrs/. When you make a non-trivial architectural call, add one. ADRs 0060–0068 cover the governance audit trail, RBAC, ICEA quality signals, project-knowledge, onboarding, dep-scan CI, cost governance, the designated Dream runner convention, and the DATA-HANDLING document.

How it all fits

Everything is declared in .claude-plugin/plugin.json — the single source of truth for the version and the component manifest. At a glance the plugin ships:

46 commands
Slash commands — thin entry points that invoke a skill or a command-delegation flow.
48 skills
The behaviour. Each is a skills/<name>/SKILL.md (+ optional references/).
43 rules
Frontmatter-scoped coding rules that auto-load per file type from a layered set.
47 shared specs
Cross-skill primitives under skills/shared/ — the contracts skills reuse.
2 subagents
bc-searcher · bc-synthesizer (business-context grounding).
Runtime hooks + CI + governance scripts
Deterministic gates, RBAC checks, audit writers, signal writers, and dep-scan CI templates that enforce the floor even when a client bypasses a prompt.
⚠Counts are authoritative from plugin.json — never hand-type them into docs. tests/validate.js checks that on-disk components match the manifest.

Component model

Commands

A command is a thin stub registered in plugin.json → components.commands. The deployable stub lives in _project-deploy/commands/<name>.md with quoted description, an argument-hint, a --help block, and a fully-qualified <skill>ai-assisted-development:<name></skill> delegation. setup-init deploys all 46 stubs into a project's .claude/commands/ so they appear in the VS Code picker. For what each command does, see the User Guide's command reference — this guide does not duplicate it.

Component model

Skills

Skills carry the behaviour. Each is skills/<name>/SKILL.md with a metadata line that declares its version, last-changed date, plugin compatibility, and a consent category.

ConsentMeaning
AMay read source freely (e.g. code generation, migration authoring).
BReads source only after announcing intent (evidence-derived doc generators).
CNever reads application source — only reports, ledgers, architecture, and state.

The authoritative table is skills/shared/source-file-consent.md; validate.py errors if a SKILL.md's token disagrees with it. Skills route to models by task type (see Model routing) and reason through named expert personas kept consistent across the suite.

Key skill changes in v3.25.0: icea-feature reads .claude/project-knowledge.md and injects applicable patterns at Step 3b, and tracks clarification_count through Steps 2–3 to write a story-quality signal at SAVE PLAN. icea-revise writes a REVISE_ADO audit event and a revision signal. icea-implement writes a gap signal when an Example cannot produce a real assertion. governance-report and onboarding-guide are new skills.

Component model

Rules

Rules are stack-scoped coding standards in _project-deploy/rules/ (43 files), organised as a layered set — base backend/frontend layers plus per-stack and per-ecosystem overrides. Each carries frontmatter that scopes it to file globs so Claude Code auto-loads only the relevant ones when editing a matching file.

Deployment is driven by scored stack-key detection (ADR 0059) so a .NET 10 API never draws legacy framework rules; the frontmatter/layering model is ADR 0042 / ADR 0043. The data-access rule is a hard one: parameterised queries only, never string-built SQL.

Component model

Shared specs

47 cross-skill primitives live under skills/shared/ and are registered in plugin.json → components.shared. They are the contracts multiple skills reuse — e.g. write-gate-spec.md, model-routing-spec.md, source-file-consent.md, multi-root-scan.md, scope-flags-spec.md, flag-prompt-spec.md, the migration ledger schema, and the offline migration-knowledge/refs/ tier.

⚠A shared spec is a single source of truth. When you add one, register it in components.shared — validate.js fails on a spec that is on disk but unregistered, and the README's shared-specs table is generated from the manifest (ADR 0063).
Component model

Hooks & subagents

Prompt-level gates are backed by deterministic hooks so the floor holds even if a client ignores an instruction: a write-blocker (icea-floor) when no approved ICEA exists, a git pre-commit hook (_project-deploy/hooks/governance-gate-precommit.cjs) that blocks commits with open Critical/High findings or pending governance violations, and a CI script that fails the pipeline on ledger-integrity violations. validate-pr-compliance.py runs as a required branch-policy check server-side — unbypassable from any client. Hooks install by default during setup-init, their integrity is monitored by setup-status, and they re-sync on every version bump.

Two subagents ship under agents/: bc-searcher (regulatory-grounding web search, no project-file access) and bc-synthesizer (combines cited categories with local architecture, no network) — the split keeps project data off the network during business-context generation.

Governance & graph

Gates & governance

The governance rails are defined in CLAUDE.md and enforced by hooks + CI + deterministic scripts. As a maintainer, know the four orthogonal gates:

Feature Gate (ICEA)
No implementation code for a new capability without an approved ICEA on disk. Output-gated; overridable only via the loud, audited /skip-icea / SKIP_ICEA_FLOOR.
Write Gate
Source/config is never written until APPROVE ADO-{ID}. Boundary-crossing writes (outside the repo root) always confirm and are not blanketed by APPROVE ALL. APPROVE ALL requires the tech_lead role (RBAC-checked at runtime).
Findings gate
Open Critical/High findings block checkin and PR creation; never blanket-skippable. Dismissing a Critical/High finding requires the security_officer role.
Critic planning gates
The critic fires at the ICEA draft, the Tech Spec draft, and generated code — before each is written (ADR 0052).

Every gate block, bypass, approval, and dismissal is recorded in a tamper-evident audit trail under .claude/audit/ (see Audit trail & RBAC below). Sprint-level governance reports aggregate the audit trail, token data, and ledger metrics — generated by scripts/governance-report.cjs and written to governance/.

Governance & graph

Audit trail & RBAC

The governance audit trail is an immutable, per-event JSON record set under .claude/audit/. Each event is committed to git, so immutability is derived from git history. RBAC is enforced at runtime by scripts/rbac-check.cjs against .claude/ApprovalRoles.json.

Audit event types

Event typeWhen it fires
APPROVE_ADODeveloper replies APPROVE ADO-{ID} — ICEA + Tech Spec approved.
APPROVE_CONFIGCI/CD or IaC config approved (requires tech_lead role).
APPROVE_ALLStanding Write-Gate batch approval granted (requires tech_lead role).
DISMISSA finding dismissed via /dismiss. Critical/High dismissals require security_officer.
BYPASS_TEST_GATEAPPROVE ADO-{ID} --skip-test-gate used (spike / prototype bypass).
BYPASS_HOTFIXHotfix path invoked — ICEA gate bypassed under emergency protocol.
RBAC_BLOCKA gated action was attempted by a user without the required role.
REVISE_ADOREVISE ADO-{ID} invoked — ICEA/Tech Spec revision started.

Event schema

Each event includes: timestamp, actor (git email), role (from ApprovalRoles.json lookup), event (type above), model (per-invocation model ID), ado_id, finding_id (for DISMISS), path, verdict, and context.

RBAC gates

Three actions require an elevated role checked at runtime via scripts/rbac-check.cjs against .claude/ApprovalRoles.json:

ActionRequired role
APPROVE ALL ADO-{ID}tech_lead
APPROVE CONFIG for CI/CD or IaCtech_lead
/dismiss of a Critical or High findingsecurity_officer

All blocked actions write a RBAC_BLOCK event. ApprovalRoles.json is seeded by setup-init Step 2d (prompts for tech leads + security officers) and its structure is { "tech_leads": [...], "security_officers": [...] }.

ℹsetup-status check 1w validates ApprovalRoles.json presence and entry counts, and reports the total audit event count in .claude/audit/.

ICEA quality signals

Quality signals are lightweight JSON files written automatically by skills to .claude/signals/. Dream's Phase 3.6 processes them — updating memory/topic-signals.md and proposing project-knowledge promotions — then deletes the signal files. The signal inbox is committed but cleared each Dream run.

Signal types

TypeWritten byWhen
gapicea-implementAn Example in the ICEA cannot produce a real assertion — a coverage gap exists.
revisionicea-reviseA section of the ICEA/Tech Spec was revised; the signal records section diff and inferred category.
story-qualityicea-featureAt SAVE PLAN: records the clarification_count — how many questions were needed to scope the feature.

Dream processing (Phases 3.5 and 3.6)

  • Phase 3.5 — staleness pass on .claude/project-knowledge.md entries: anchor check (does the referenced code still exist?) + age threshold (entries older than the configured age are flagged for review).
  • Phase 3.6 — processes all .claude/signals/ files: updates memory/topic-signals.md tally, proposes a project-knowledge ADD when the count for a topic reaches gap_promotion_threshold (default: 2), then deletes the signal files.

Designated Dream runner

One team member — typically the Tech Lead — is designated as the Dream runner per sprint. This convention avoids merge conflicts that arise when multiple developers run /dream independently against the same memory/MEMORY.md. The designated runner is recorded in ApprovalRoles.json and shown by setup-status.

ℹThe signal scripts are scripts/signal-write.cjs (writes signals) and scripts/governance-report.cjs (aggregates audit + token + ledger data for sprint reports). Neither modifies source.
Governance & graph

Project knowledge

.claude/project-knowledge.md is a per-project pattern library that accumulates what the plugin learns about a specific target application across all ADOs and releases. Its sole purpose is to improve future ICEA writing and implementation quality — it is not memory/MEMORY.md (developer decisions, errors, architecture choices) and not ai-audit.md (per-ADO governance). The team multiplier: a pattern discovered by Developer A on ADO-1234 improves Developer B's ICEA six months later on ADO-5678, eliminating redundant discovery and repeated revision cycles.

Entry format

project-knowledge.md entry
### [{N}] {short title}
Source ADO  : ADO-{ID} [, ADO-{ID}]
Added       : {YYYY-MM-DD}  Release {R}
Code anchor : {ClassName or InterfaceName}   ← optional; used for auto-validation
---
{Pattern — 1–3 sentences, concrete and actionable.}

The Code anchor field is an optional class or interface name. Dream uses it for automated staleness checking — if the anchor disappears from src/, the entry is flagged for removal.

What belongs

  • Recurring dependency patterns — "service layer always needs IUserRepository — declare in ICEA Context"
  • Team naming conventions discovered from code — "test classes follow {ClassName}Tests pattern"
  • ICEA anti-patterns that caused revision cycles — "Examples must specify return object shape, not just method name"
  • Stack-specific patterns unique to this codebase — "Repository pattern throughout — unit tests need IRepository<T> mock"
  • AC conventions — "every endpoint AC must specify the HTTP status code for success and error cases"

General language/framework best practices belong in rule files. Anything already in architecture.md does not belong here (duplication creates drift). Transient information (sprint goals, one-time setup steps, status updates) also does not belong.

Three-layer staleness defence

LayerMechanismDeveloper action
1 — Code anchor checkAt Dream time: grep for the anchor in src/. If missing → flag ⚠ ANCHOR MISSING → propose REMOVERespond inline during /dream: KEEP-{N} / REMOVE-{N} / UPDATE-{N}
2 — Age thresholdEntries older than 180 days (or 2 releases) are flagged ⚠ AGE THRESHOLD → proposed for REVALIDATE regardless of anchor statusSame inline response during /dream. UPDATE-{N} opens a follow-up prompt for corrected text.
3 — LLM framingicea-feature reads the file with a built-in guard: "treat as patterns observed at a point in time — verify against the current codebase before applying, flag conflicts"None — passive. The LLM flags stale entries during ICEA drafting before the developer sees the plan.

Dream management lifecycle

During /dream, project-knowledge entries are checked as a second pass — after MEMORY.md, before Phase 4. For each flagged entry Dream proposes REMOVE, REVALIDATE, or KEEP. The developer responds inline:

dream response syntax
KEEP-{N}      ← accept as-is, no change
REMOVE-{N}    ← delete the entry
UPDATE-{N}    ← opens a follow-up prompt for replacement text

All writes go through the standard Write Gate — no ADO ID required. Treated as plugin infrastructure alongside ApprovalRoles.json.

ℹThe authoritative spec is skills/shared/project-knowledge-spec.md. The icea-feature skill reads this file at Step 3b and injects applicable patterns into the ICEA drafting context.

Governance & graph

Knowledge graph internals

The codebase knowledge graph in .claude/graph/ is the single orientation layer. graph.json is the authoritative structure — typed nodes/edges with confidence, module-wide staleness fingerprints, and an absent-tolerant sourceRoot for multi-root repos — and the markdown index + per-module detail files are its projection (ADR 0039).

EXTRACTED dependency edges are derived deterministically from source imports by scripts/graph-extract-edges.js (not by the model), so they are parser-true and byte-stable and source never enters context (ADR 0041); the model authors only INFERRED/AMBIGUOUS edges. module-derive.cjs derives the module skeleton (multi-root aware via multi-root-scan.md); graph-create builds the initial graph at setup and graph-sync refreshes it incrementally.

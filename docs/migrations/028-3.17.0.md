# Migration 028 — v3.17.0

## Summary

Rule deployment is now driven by **scored stack-key detection** (ADR 0059). The detector
(`repo-detect.cjs` + new `scripts/stack-signals.cjs`) emits a `detection` object with confidence
scores + nested runtime generation; `stepDeployRules` deploys only rule files whose `stack_key`
crosses the confidence threshold (default 0.6), by the `${stack_key}-rules.md` convention, with
hash-tracked overwrite and a `_deploy-manifest.json` audit trail. This fixes wrong-stack
deployment (e.g. a .NET 10 API drawing `css`/`javascript`/`ado-net-legacy`/`csharp-framework48`).

## Change type

New detection module + rewritten rule-deploy step + `detect:` frontmatter stripped from all rule
files + setup-status/setup-sync/setup-teardown updates. Applied by `/setup-sync`.

## Required action

Run `/setup-sync`. Step 3 now **re-runs detection (`repo-detect --force`) + the scored deploy**,
writing `.claude/rules/.hashes` + `.claude/rules/_deploy-manifest.json`. Developer-edited rules
are protected (hash-tracked, warn + skip).

> **Dropping already-deployed wrong rules:** re-deploy is idempotent-**add** — it (re)writes the
> correct set + manifest but does NOT delete rules no longer detected (avoids clobbering
> developer-edited files). To remove stale rules from a mis-provisioned project, run
> `/setup-teardown --rules` (now also clears `.hashes` + `_deploy-manifest.json`) then
> `/setup-sync`.

## Sync actions (idempotent — never overwrite developer content)

1. `repo-detect.cjs --force` refreshes the scored `detection` in `dream-init-state.json`
   (pre-3.17 installs have none).
2. `setup-init-bootstrap.cjs --mode post-detect` re-runs `stepDeployRules` → threshold deploy,
   `.hashes`, `_deploy-manifest.json`, `deployed_rules[]` (retained for teardown).
3. setup-status now reports rule presence from `_deploy-manifest.json` (fixes the pre-existing
   stale-name bug where correctly-deployed `csharp-dotnet-rules.md` was reported MISSING).

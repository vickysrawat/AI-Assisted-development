## Item 3 — Target-project test integration (gate + generated unit tests)
**Status:** ✔ Done · 2026-09-20

_Clarification (2026-09-20): Item 1 built the plugin's own test framework. This item is about what the plugin does for test discipline in target projects. Two sub-problems: (1) a gate that blocks `APPROVE ADO-{ID}` unless a test plan exists on disk; (2) unit tests generated by `IMPLEMENT ADO-{ID}` alongside source files._

_Terminology settled: "generated unit tests" — not "scaffold" or "stub". The ICEA Examples section contains concrete input/output pairs in prose; the LLM translates them to real assertions (`Assert.Equal`, `expect().toBe()`, etc.). TODOs are only emitted where the ICEA genuinely lacks information (complex mock contracts, domain edge cases not enumerated) and are explicitly flagged so the developer knows exactly what's missing — not left as silent gaps._

**Key constraint — ICEA gap is an ICEA defect, not a test gap (agreed 2026-09-20):**
If test generation cannot produce a real assertion for an Example — because the input/output pair is underspecified, a dependency contract is missing, or a required edge case is not described — that is not a testing problem. It means the ICEA did not fully model the blast radius of the feature. The plugin must reverse-flag the ICEA with a specific annotation ("Example 3 is underspecified: dependency `IUserRepository.GetById` return contract not described") and block implementation until the ICEA is revised. This makes the ICEA process self-correcting in real time. Gap signals from this item feed Item 9 (per-project learning loop).

| Field | Detail |
|---|---|
| Risk if skipped | A team can APPROVE and ship code with zero tests. The test-plan skill generates a document but nothing enforces it. No gate, no generated tests = test discipline is entirely voluntary. |
| Trade-offs | Gate blocks fast approvals — mitigated by `--skip-test-gate` bypass (audited, not silent). Test generation from ICEA Examples requires Examples to be well-specified — but that is a feature, not a problem: under-specified Examples surface ICEA defects early. |

If ambiguous or no existing tests, one-time prompt stored in `dream-init-state.json` (never asked again). |

## Item 9 — Per-project learning loop
**Status:** ✔ Done · 2026-09-20

_Depends on: Item 3 (test generation gap signals). Discuss after Item 3 is built._

**What this is NOT:**
- Not `ai-audit.md` — ADO-level governance, one file per story, fragmented across `docs/Release{R}/Sprint{S}/UserStory{ID}/`
- Not `memory/MEMORY.md` — memory IS in the target application repo root and tracks developer decisions on that application (architecture, errors, approaches). Project-knowledge is a separate concern: patterns that improve ICEA quality, not decisions.

**What this IS:**
A new project-level artifact — `.claude/project-knowledge.md` — that accumulates what the plugin learns about *this specific target application* across all ADOs and all releases. Scoped exclusively to patterns that improve ICEA writing and implementation. Read by `icea-feature` at planning time so every ICEA draft starts with accumulated team knowledge, not a blank slate.

**Content model — what belongs in it:**
- Recurring dependency patterns ("service layer always needs `IUserRepository` and `IEmailService` — declare in ICEA Context")
- Team naming conventions discovered from code ("test classes follow `{ClassName}Tests` pattern")
- ICEA anti-patterns that caused revision cycles ("Example must specify return object shape, not just method name")
- Stack-specific patterns unique to this codebase ("Repository pattern throughout — all unit tests need `IRepository<T>` mock")

Each entry carries: content · source ADO(s) · date added · release added · optional source-code anchor (interface/class name for auto-validation).

**Population — two paths:**
1. **Automatic promotion**: when test generation (Item 3) flags the same ICEA gap across 2+ ADOs, the pattern is promoted with source ADOs referenced
2. **Manual via `LESSONS ADO-{ID}`**: handler prompts "does this lesson belong in project-knowledge.md?" — developer confirms

**Staleness — three-layer defence:**
1. **Source-code anchor check**: entries tied to a code construct (interface, class) are auto-verified at Dream time — if the construct no longer exists, the entry is flagged FAILED
2. **Age threshold**: entries older than 2 releases are flagged ⚠️ for revalidation regardless of anchor status
3. **LLM framing**: `icea-feature` reads the file with explicit instruction — "treat as patterns observed at a point in time; verify each against current codebase before applying; flag conflicts rather than silently following a stale entry"

**Management — Dream as the review + write cycle:**
Dream is extended to manage both `memory/MEMORY.md` and `.claude/project-knowledge.md` in two distinct sections of its health report. During a Dream run, flagged entries are presented with a proposed action per entry and the developer responds inline:

```
§ Project Knowledge — .claude/project-knowledge.md
  8 entries · 1 ⚠️ anchor missing · 1 ⚠️ age threshold reached

  Entry #4 — IUserRepository mock setup (Release 2 Sprint 1, 8 months ago)
    ⚠️ Anchor FAILED — IUserRepository not found in codebase
    Proposed: REMOVE
    → Reply KEEP-4 / REMOVE-4 / UPDATE-4

  Entry #7 — Test naming convention (Release 3 Sprint 2, 4 months ago)
    ⚠️ Age threshold reached
    Proposed: REVALIDATE — still the team convention?
    → Reply KEEP-7 / REMOVE-7 / UPDATE-7
```

Developer replies (e.g. `KEEP-7 REMOVE-4`) → Dream writes the updated file through the standard write flow. `UPDATE-N` opens a follow-up prompt for the corrected text.

**Immediate correction (outside Dream):**
```
KNOWLEDGE REMOVE {N}   — remove entry N now
KNOWLEDGE UPDATE {N}   — edit entry N (prompts for new text)
KNOWLEDGE ADD          — add a new entry manually
```

**The team multiplier**: Developer A discovers a pattern on ADO-1234 → promoted to `project-knowledge.md` → Developer B starts ADO-1567 months later → `icea-feature` reads the file and proactively includes the pattern in the ICEA draft. Developer B never hits the gap. One developer's learning benefits the whole team across all future releases.
